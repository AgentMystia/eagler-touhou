# 缓存与兼容

## 必须区分的状态

| 状态 | 拥有者 | 更新原则 |
| --- | --- | --- |
| 源码构建缓存 | 构建工具 | 输入身份变化后重新生成 |
| App Shell 与 Runtime 入口 | Service Worker | 验证候选资源图后切换，保留旧客户端需要的代次 |
| 游戏 Package | 浏览器存储服务 | 完整校验后提交 current，失败不替换已可用代次 |
| 存档、Replay、设置 | 对应存储模型 | 按各格式迁移或导入；不能当作可随意清空的编译缓存 |
| 站点资源清单 | 打包工具 | 描述同一次交付的实际文件及哈希 |

哈希用于身份和完整性。协议行为仍需执行验证；文件内容与某个历史哈希相同不代表功能完整。

## 构建缓存

`lib/contracts-build.mjs` 为共享 contracts 生成不可变代次。输入身份覆盖实际编译依赖，并在构建前后复核，防止编译期间输入改变后仍发布混合结果。Worker 的资源闭包也进入其产物身份。

`lib/client-services-build.mjs` 目前仍使用 `.cache/build/browser` 和目录锁。进程异常退出后可能需要排查残留锁，当前机制没有持锁进程身份和自动恢复证据。后续应改为不可变构建代次及明确发布步骤，配合真实并发/崩溃测试。不要在另一个构建仍运行时删除锁。

## 浏览器离线与更新

首个在线访问需要完成 App Shell 安装；游戏需要完成相应 Package 安装。浏览器存储仍可能因用户清理、隐私模式、容量策略或更换 Origin 而丢失。

候选 App Shell 不完整、某个未选 Runtime 损坏或更新中断时，系统应继续使用可用代次。测试包含实际 Service Worker、跨浏览器进程离线启动和嵌套挂载路径。测试中的合成游戏只证明资源图和启动协议，不能证明所有作品在目标设备上能运行。

刷新旧标签页和启动新标签页可能暂时使用不同代次；各自必须保持清单与资源一致，不能只替换单个无版本入口。

## 保留兼容的依据

`compat/`、`contracts/src/compat/` 及资源模式解析器只为已存在的持久化格式、已发布清单或浏览器早期入口提供读兼容。每个保留分支应有对应旧格式输入和目标行为。

历史 `import-only`、`import-partial` 可读兼容不成为新的输出模式。当前站点只生成 hosted、external、import。遗留资源 URL 的迁移优先在资源站点完成，不能无限扩张前端路径猜测。

旧版界面源码、旧 CSS 快照和临时迁移注入器不是兼容接口。测试直接运行当前组件；兼容测试使用必要的旧数据或旧发布产物。

## 排错

先判断失败属于网络、存储、Runtime 还是编译缓存。记录失败的资源、代次、阶段和错误类型。保留用户存档与 Replay 后再执行任何清理；不要用“清空所有数据”掩盖代次混用或取消失效。

更改缓存或兼容行为时，参照[验证 playbook](../../../docs/playbooks/verification.md)，至少复现正常路径、候选失败和已有可用代次继续运行。
