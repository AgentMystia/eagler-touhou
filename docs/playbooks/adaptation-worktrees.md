# 适配源码与工作区

## 明确源码拥有者

游戏适配使用任务指定的源码仓库、分支和提交。上游参考用于核对原行为，普通/多人 Runtime 使用对应 Eagler 源码。工程入口只消费明确的源码目录，不创建、切换或重置 worktree。

在本项目中，根目录 `th06`—`th11`、`th15` 是锁定的游戏子模块。维护者的外部 canonical checkout 和实验目录可以作为显式 `--source` 输入，但不能因为目录名熟悉就代替当前 gitlink。

## 实施前

1. 记录目标源码的 HEAD、分支和未提交修改。
2. 核对其递归 common 与 SDL 等依赖的实际提交。
3. 阅读对应功能的 playbook，并从它的代码入口继续。
4. 选择本次普通、多人或诊断变体，明确资源和输出目录。

需要隔离实验时，由任务明确决定是否创建工作区，并记录来源和用途。不要将旧规则中的固定实验目录或自动四条实验线当作构建前提。

## 合并与交付

核对实验的真实祖先：多人分支的实验以该多人源码为基线，不能仅凭都叫 Eagler 就合入普通分支。保留原有未提交修改，解决冲突后重新执行受影响的构建和行为检查。

子依赖先保存并发布可获取的提交，再由父仓库记录 gitlink。实际发布前从空目录初始化递归依赖，确认不依赖本机已有 Git 对象或私有目录。实验产物、诊断导出和未验证能力不自动变成正式 Runtime 的内容。
